# AgroSpace Quest — Risk Register

**Last updated:** 2026-11-05  
**Status:** Phase 0 planning register; probabilities and impacts are qualitative planning assessments, not measured frequencies. Owners are proposed team roles and should be confirmed by the team.

| ID | Risk | Probability | Impact | Trigger / warning sign | Mitigation | Owner | Fallback | Resolve / review phase |
|---|---|---|---|---|---|---|---|---|
| R1 | NASA service outage, high latency, authentication changes, or rate limiting interrupts collection/demo. | Medium | High | Repeated timeout/5xx responses, login rejection, or throttling during pre-demo checks. | Bound timeouts/retries; cache successful responses; check official service guidance; test a representative request before UI integration. | Person A — Backend/Data | Use clearly labeled cached fixture data for the demo; show source age and unavailable status. | Phase 3 |
| R2 | Required NASA product/parameter is unavailable for chosen coordinates/date range or API support differs from assumptions. | Medium | High | Requested variable absent, invalid coordinate/date response, or unsupported product/access path. | Verify exact product, parameter, coverage, units, and access path before implementation; retain a second indicator/source only if verified. | Person A + Person C | Drop unsupported variable and explain the data gap; do not substitute an undocumented value. | Phase 3 |
| R3 | Source spatial support is too coarse for a small farm. | High | High | Product footprint exceeds farm size or covers multiple farms/land-cover types. | Store support per product/parameter; display scale honestly; avoid unsupported field-level claims and false precision. | Person A + Person C | Present regional context only or omit it from farm-specific recommendations. | Phase 0 design; Phase 3 verification |
| R4 | NASA, soil, and crop sources use incompatible temporal calendars, spatial support, units, or definitions. | Medium | High | Aggregation requires undocumented conversion, mismatched season windows, or incompatible spatial join. | Preserve original units/support/time convention; document transformation and version; define aggregation only for a stated use. | Person A — Data; Person C — Agronomy | Keep sources separate and show uncombined contextual evidence until a valid harmonization method exists. | Phases 3–5 |
| R5 | Missing, cloudy, or poor-quality satellite observations are interpreted as negative evidence or farmer failure. | Medium | High | QA/coverage flag is missing/poor, or a UI/rule maps missing data to zero or a penalty. | Carry QA/coverage status; distinguish missing from zero; never penalize users for missing/inconclusive observations. | Person A + Person B | Mark claim unavailable and require self-report or human review; do not award/withhold verification points from missing data. | Phases 3–4 and 8 |
| R6 | No verified regional crop calendar or agronomic rules are available for the selected region. | High | High | Region selected but no authoritative source or reviewer confirms a candidate crop/season rule. | Team selects region/persona; Person C sources minimum crop/season facts from credible extension, FAO, or peer-reviewed material; seek local review; label demo rules. | Person C — Agronomy/UX | Restrict prototype to sourced entries or show no recommendation for unsupported seasons; do not let an LLM invent rules. | Phase 0 decision; Phase 5 resolution |
| R7 | Farmer soil test is unavailable or incomplete, causing unsupported soil claims. | High | Medium | Required lab value, sample date/depth, method, or source is absent. | Treat null as unknown; record method, sample date/depth and source; separate farmer-provided tests from modeled fallback. | Person C + Person A | Continue with soil-dependent claims marked not assessed; omit unsupported soil regeneration benefit. | Phases 2 and 5 |
| R8 | Recommendations appear more certain than evidence or imply guaranteed yield/water/soil outcomes. | Medium | High | Numeric benefit has no traceable source/method, or confidence is copied from completeness. | Use structured evidence, explicit assumptions/data gaps, claim-specific confidence rubric or `NOT_ASSESSED`; prohibit unsupported quantitative benefit claims. | Person C + Person A | Return fewer claims/options or block generation with missing-evidence details; require local expert review. | Phase 5 |
| R9 | PostGIS/Redis setup friction on team machines, especially Windows, consumes hackathon time. | Medium | Medium | A team member cannot reproduce documented database/broker startup in a clean environment. | In Phase 1 document supported versions and repeatable commands; prefer Docker Compose for PostGIS/Redis with Django/Vite local if supported. | Person A + Person B | Document exact supported local install versions and reduced development mode; do not silently switch to SQLite for spatial acceptance. | Phase 1 |
| R10 | API contract drift between backend and frontend. | Medium | High | Frontend fixture and backend response differ in field name, enum, nullability, or status semantics. | Agree contracts before implementation; keep `API_CONTRACTS.md` current; use representative fixtures and contract review at integration. | Person A + Person B | Freeze a minimal versioned response shape and coordinate changes before either side merges. | Phases 1–9 |
| R11 | Agent-generated changes or migrations break working modules or introduce inconsistent schemas. | Medium | High | Unexpected diff, migration conflict, or previously working module fails after an isolated change. | Work in small phase-scoped changes; inspect migrations/diffs; preserve ownership boundaries; review before integration; keep version control checkpoints. | All; phase lead accountable | Revert isolated change and restore last known working checkpoint; defer nonessential scope. | All implementation phases |
| R12 | Hackathon time overrun and scope creep displace the end-to-end farmer journey. | High | High | Optional integration or polish consumes planned P0 time before core journey works. | Protect P0 vertical slice; hold GPM, report export, 80% gate, LLM, advanced GIS, and rewards to P1 unless core journey is complete. | Team; coordinator to be named | Cut optional work and demonstrate the complete supported journey with honest gaps. | Continuous; review at each phase |
| R13 | Region, farmer persona, crop system, and stable region code remain undecided, blocking calendar/crop work. | Medium | High | Phase 5 planning begins without an explicit team selection and configured region code. | Record an explicit team decision before seeding regional knowledge; retain data-driven `region_code`. | Team | Keep region-dependent APIs configurable and defer regional recommendation examples until selected. | Phase 0 / before Phase 5 |
| R14 | Documentation/API examples are mistaken for verified measured results. | Medium | High | Fixture is rendered without an illustrative label or numeric claim appears without evidence ID. | Mark fixtures illustrative; use null/not-assessed values; distinguish USER_PROVIDED, reanalysis, retrieval, modelled, derived, and scenario data. | All; doc owner is project lead | Remove numeric examples or replace with schema placeholders until verified. | Phase 0; recheck Phase 9 |

## Review cadence

Review the register at phase boundaries and whenever a risk trigger occurs. Update probability, impact, mitigation, owner, fallback, and resolution phase as facts change. A risk is not closed merely because its phase ended; record the evidence for closure or carry it forward.
